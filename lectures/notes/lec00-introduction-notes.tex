\section{What the course studies}
\textit{Source: pp.\ 2--13.}

A \textbf{data structure} is a way of storing and organizing data so that the required operations can be performed efficiently. An \textbf{algorithm} is a procedure that operates on that data to solve a problem. Choosing them together matters: a representation that makes one operation fast may make another slow.

The course moves from writing working programs to explaining why programs are efficient. Its main goals are to understand abstract data properties, design and analyze algorithms, compare representations, and implement them in Java.

\subsection{Logical organization versus physical representation}
\begin{itemize}
\item \textbf{Logical organization:} how the data relate to each other, such as a linear list, hierarchy/tree, network/graph, or set/map.
\item \textbf{Physical representation:} how the program stores the data, such as an array or linked nodes. The same logical structure may have several implementations.
\end{itemize}

For a phone book, the data are names and phone numbers; the operations include insertion, deletion, and lookup. An unsorted list, an ordered list, and a search tree offer different tradeoffs. For a campus map, vertices represent buildings and weighted edges represent distances. The graph can be stored using a matrix or adjacency lists; finding a shortest route is an algorithm on that representation.

\section{Arrays}
\textit{Source: pp.\ 29--33.}

An array is an indexed sequence with a \textbf{fixed capacity}. Java arrays contain values of one declared component type. A primitive array stores primitive values; an object array stores references to objects.
\begin{lstlisting}[language=Java]
int[] x = {3, 1, 7, 5};
int[] y = new int[4];    // initially {0, 0, 0, 0}
String[] words = new String[4]; // initially null references
\end{lstlisting}

Distinguish \textbf{size} $n$, the number of elements currently used, from \textbf{capacity} $N$, the number of slots allocated. Valid occupied indices are $0,\ldots,n-1$.

\begin{itemize}
\item \textbf{Access or replacement at index $i$:} constant time, $O(1)$, because the slot can be addressed directly.
\item \textbf{Insert at index $i$:} shift $n-i$ elements one position right, then store the new element. Shift from right to left to avoid overwriting unread elements.
\item \textbf{Delete at index $i$:} shift $n-i-1$ later elements left to close the gap. Clear the vacated reference slot when appropriate.
\item \textbf{Insert into a full array:} allocate a larger array and copy existing elements. The old array itself does not change length.
\end{itemize}

\textbf{Example.} Inserting $7$ at index $2$ in $[3,1,5]$ requires moving $5$ right, producing $[3,1,7,5]$. Insertion at index $0$ moves every existing element, so its worst-case time is $O(n)$.

\section{Singly linked lists}
\textit{Source: pp.\ 34--38, 43.}

A singly linked list is a sequence of nodes. Each node contains an element and a reference to its successor. A \texttt{head} reference identifies the first node; the last node's \texttt{next} is \texttt{null}.
\begin{lstlisting}
head -> [3 | next] -> [1 | next] -> [7 | next]
     -> [5 | null]
\end{lstlisting}
The nodes need not occupy adjacent memory. Accessing index $i$ requires following $i$ links from the head: $O(i+1)$ time, or $O(n)$ in the worst case.

\subsection{Insertion and deletion}
Given a reference to the predecessor \texttt{pred}, inserting after it takes a constant number of reference updates:
\begin{lstlisting}
newNode = new Node(e, pred.next)
pred.next = newNode
\end{lstlisting}
Deleting the successor also takes constant time:
\begin{lstlisting}
removed = pred.next
pred.next = removed.next
\end{lstlisting}
These bounds \textbf{exclude finding the predecessor}. If the input specifies only an index, a traversal may be required first.

At the head, insertion sets \texttt{newNode.next = head} and then \texttt{head = newNode}; removal sets \texttt{head = head.next}. Empty-list cases must be handled before dereferencing a node.

\subsection{What does a tail reference buy?}
With a maintained tail reference, appending is $O(1)$: connect the old tail to the new node, then update the tail. When initially empty, set both head and tail to the new node.

Removing the last node is still $O(n)$ in a singly linked list: the tail does not identify its predecessor. A traversal is needed to find the new last node. When removing the only element, set both head and tail to \texttt{null}.

\subsection{Java generics}
The slides generalize an integer list to \texttt{SLListG<MyType>}. A type parameter lets the same implementation store different reference types, such as \texttt{Integer} and \texttt{String}. Java generic arguments use reference types; \texttt{Integer} is the wrapper corresponding to primitive \texttt{int}.

\section{Doubly linked lists}
\textit{Source: pp.\ 39--42.}

Each node stores an element, a \texttt{prev} reference, and a \texttt{next} reference. Both directions are available, so a known node can be removed without searching for its predecessor.

To insert between adjacent nodes \texttt{pred} and \texttt{succ}:
\begin{lstlisting}
newNode.prev = pred
newNode.next = succ
pred.next = newNode
succ.prev = newNode
\end{lstlisting}
To remove an interior node \texttt{p}:
\begin{lstlisting}
p.prev.next = p.next
p.next.prev = p.prev
\end{lstlisting}
Both operations are $O(1)$ when the relevant nodes are already known. In an implementation without dummy nodes, endpoint updates need special handling. \textbf{Header and trailer sentinels} simplify these cases: they remain in the list but contain no user elements. An empty sentinel list has \texttt{header.next = trailer} and \texttt{trailer.prev = header}.

Unlinking an object makes it eligible for garbage collection only if no reachable references to it remain. Garbage collection is not necessarily immediate.

\section{Comparison to remember}
\textit{Source: p.\ 44; complexity details explained above.}

All times below are worst-case. The array has spare capacity; both linked lists maintain head and tail references.
\begin{center}
\small
\begin{tabularx}{\textwidth}{Xccc}
\toprule
Operation & Array & Singly linked & Doubly linked\\
\midrule
Access by index & $O(1)$ & $O(n)$ & $O(n)$\\
Search for a value & $O(n)$ & $O(n)$ & $O(n)$\\
Insert at front & $O(n)$ & $O(1)$ & $O(1)$\\
Append & $O(1)$ & $O(1)$ & $O(1)$\\
Remove last & $O(1)$ & $O(n)$ & $O(1)$\\
Remove known interior node & $O(n)$ & $O(1)^*$ & $O(1)$\\
\bottomrule
\end{tabularx}
\end{center}
$^*$For the singly linked list, the predecessor must also be known. For the array, the index is known and later elements must shift.

Array storage is $O(N)$; linked storage is $O(n)$ with extra references per node. Arrays support fast indexed access. Linked structures support fast local changes once the relevant position is available.

\section{Quick review}
\begin{enumerate}
\item Why is a tail reference insufficient for fast singly linked tail deletion?\\
\textbf{Answer:} deletion needs the previous node, which cannot be reached by following the tail's forward link.
\item Does constant-time linked insertion imply constant-time insertion by index?\\
\textbf{Answer:} no. Finding the position may take linear time.
\item How many elements shift when inserting at index $i$ in a size-$n$ array?\\
\textbf{Answer:} $n-i$, assuming sufficient capacity.
\item What is the difference between logical organization and implementation?\\
\textbf{Answer:} a logical list specifies an ordered collection; arrays and linked nodes are possible storage representations.
\end{enumerate}

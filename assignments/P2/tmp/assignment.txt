                                 Reconnecting the Neighborhood

Problem Description

After a severe storm, a neighborhood's road intersections must be repaired before delivery vehicles can use them.
Crews reopen intersections in stages. In each stage, some intersections are repaired and reconnected to their open
neighbors. A response team needs to monitor the neighborhood's connectivity and the available delivery routes from
supply depots to destinations as repairs progress. In this assignment, the neighborhood is modeled as a rectangular
street grid, where vertices represent intersections, and edges represent roads. Each road has a fixed travel time that
can differ from that of other roads.
Your program will produce a report after each repair stage, showing the connected regions, the fastest routes, and the
critical roads for specified deliveries.

1 How the road network works

The road grid has  rows and  columns, where ,   1. Let  =  denote the total number of intersections
(vertices). Rows are numbered from 0 to  - 1 and columns from 0 to  - 1, with (0, 0) at the upper-left corner.
Intersection (, ), located at row  and column , has an integer identifier , given by

Conversely, the intersection with identifier  is located at row / and column  mod .
Each intersection has one of two states: blocked or open. A blocked intersection has not yet been repaired and cannot
be used by delivery vehicles. An open intersection has been repaired and can be used. Initially, all intersections
are blocked. Two intersections are neighbors if one is immediately above, below, to the left, or to the right of the
other. Note that two intersections with consecutive identifiers may not be neighbors: for example, when ,  > 1,
intersections  - 1 and  are not neighbors. A road connects each pair of neighboring intersections, and a road is
usable when both intersections are open. Opening an intersection makes all roads to its open neighbors usable.
Each delivery request specifies a source  and a destination . A delivery route from  to  is a sequence of open
intersections that starts at  and ends at , with a usable road connecting each consecutive pair. A source-destination
pair (, ) is reachable if there exists a delivery route between  and . All roads are undirected and have fixed
positive integer travel times, in seconds. A delivery route's travel time is the sum of the travel times of its roads.

In each stage, newly repaired intersections become open, which can make additional roads usable and change the
network status.

First, the connectivity and open components could change. A connected region, also called an open component,
consists of an open intersection together with all other open intersections reachable from it through usable roads. An
isolated open intersection forms a component on its own; blocked intersections do not belong to these components.

Second, the delivery route between each source-destination pair could change. A delivery route may initially require
a long detour. As more intersections reopen, a faster route may become available.

In addition, for a source-destination pair that currently has a delivery route, a usable road is critical if removing that
road alone would leave no route between that pair. It is non-critical for the pair if delivery would still be possible
without it. A road can be critical for one source-destination pair and non-critical for another. As more intersections
reopen, the critical roads for each source-destination pair could also change.

2 Assignment overview and programming tasks

Your goal is to monitor and analyze the network as repairs are completed in stages.

The report for each stage contains three parts:

  · Connectivity and open components. Give the number of open intersections, the number of open components,
    and the size of each component. For each monitored source-destination pair, report 1 if it is reachable and 0
    otherwise.

  · Fastest routes. For each reachable source-destination pair, give a delivery route with the minimum total travel
    time and report that time. For an unreachable pair, report -1.

  · Critical roads. For each reachable pair, list all the critical roads, i.e., the roads whose individual failure would
    disconnect the pair. Report [] if no road is critical, or -1 if the pair is unreachable.

In stage 2 of Example 1, the call shortestRoute(network,0,11) returns time 7 and route [0, 4, 5, 1, 2, 6, 10, 11].
Priority queue implementation in Dijkstra's algorithm. Java's PriorityQueue does not have a decrease-
key method. To implement Dijkstra's algorithm, use the provided HeapAdaptablePriorityQueue from
net.datastructures:

 HeapAdaptablePriorityQueue<Long, Integer> pq = new HeapAdaptablePriorityQueue<>();

Insert each open vertex once using pq.insert(dist[v],v) and retain the returned Entry<Long,Integer>.
When dist[v] improves, call pq.replaceKey(entry,dist[v]) to update the existing key and restore heap order.
Use pq.removeMin() to remove the minimum entry, and entry.getKey() and entry.getValue() to read its
distance label and vertex identifier. See Section 9.5 in the textbook for more implementation details of the adaptable
priority queue.

2.3 Part 3: Critical Delivery Roads

The RoadAnalysis class. This class identifies the critical roads for one monitored pair. Its input is the GridNetwork
object and one source-destination pair. You implement criticalRoads in this class, with a private depth-first
search (DFS) helper if needed.

 public static int[][] criticalRoads(GridNetwork network, int source, int target)

Result. Return an int[][] with one {u,v} row for each critical road, where  < , with no duplicates. The rows
may be in any order. Return an empty array if either endpoint is blocked, the pair is unreachable, or no road is critical.

How to identify critical roads. Run DFS from the source. Consider a tree edge (, ), where  is the parent of .
If a vertex in 's subtree has a back edge to  or an ancestor of , that back edge provides a detour around (, ).
Otherwise, removing (, ) separates the subtree from the source, so the road is a bridge (or critical road in our
context). The following information helps us detect these detours:

  · parent[v] records the parent of  in the DFS tree.
  · disc[v] records the discovery order of : use 0, 1, 2, and so on, and -1 for an unvisited vertex. A smaller

    number means an earlier discovery.
  · low[v] is the smallest discovery number reachable from  by following zero or more tree edges downward and

    then at most one back edge to an ancestor. Intuitively, it records how far back a back edge from this subtree can
    reach. When  is first visited, initialize low[v] = disc[v].

Examine each open neighbor  in network.neighbors[v] in the stored order:

  · If  is unvisited, set its parent to  and visit it recursively. After the recursive call returns, update low[] =
    min{low[], low[]}. This carries information about back edges in 's subtree up to .

  · Otherwise, if   parent[] and disc[] < disc[], the road to  is a back edge. Update low[] =
    min{low[], disc[]}. Ignore the edge back to the parent: it is the same undirected road, not a detour.

Complete the DFS so that all low values are final. If the target was not reached, return an empty array. Otherwise,
follow parent from target back to source. A tree edge (, ) on this path is critical exactly when

                                                          low[] > disc[].

This means that 's subtree cannot reach  or an earlier ancestor through a back edge. The inequality is strict:
reaching  itself already provides a detour. Bridges outside the source-to-target tree path are not critical for this pair.
